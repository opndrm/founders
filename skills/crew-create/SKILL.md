# Crew Create

Crew Create prepares Captain-approved Crew product slices. **Crew Watch** is one major, named milestone within Crew: a durable, always-on supervision layer for real JCode Swarm work. It is not a rebrand of the Crew product or every Crew creation.

Turn a Captain-approved Crew idea into a small, truthful request for JCode, Crew’s exclusive implementation harness. Use `/crew` first for the full operating context, then use this skill to prepare the next build slice.

## Crew Watch milestone

Treat Crew Watch as a future JCode-native Rust capability. It must reuse verified JCode primitives for Swarm ownership, lifecycle events, completion reports, explicit wake or assignment, task-plan state, message acknowledgement, and Mermaid/status projection.

Crew Watch may add only the supervision gaps proven absent from JCode: durable pending-event state, one verified supervisor owner per repository, liveness/timeout observation, bounded recovery, and escalation of an unacknowledged message or actionable failure. It must never become a second scheduler, agent runtime, model router, message broker, or autonomous review loop.

Crew Watch observes Crew lifecycles; it does not rename them. A Crew creation attaches a named identity to a real JCode Swarm member, preserves its Captain/repository/parent scope, records evidence, and returns scope-changing decisions to the Captain.

## Future native `/crew create` command contract

Treat this as the foundation for a future JCode-native command, not a currently implemented capability.

The future `/crew create` command will create a Crew inside JCode Swarm by collecting and validating:

- one Captain with a chosen display name and JCode-selected model route;
- one repository or project mandate, a bounded lifecycle or current task, and explicit success criteria;
- named Crew members, each with an `@name`, selected route, scoped responsibility, parent Captain, and stable native identity;
- the native capacity and deep-Swarm policy supplied by JCode.

Use the Crew size the Captain directs, bounded only by JCode's verified active capacity and provider admission. Do not impose a fixed three-member limit. Each additional member requires a concrete task, parent accountability, and a report-back path.

JCode must validate model routes, names, repository scope, and capacity before it creates real Swarm work. Reject duplicate or reserved names and unavailable routes. Do not silently fall back to another model or create a second scheduler, roster database, channel server, or worker runtime.

## Future Captain, Crew, and Mermaid status

The native JCode Mermaid projection will show real, derived state for the Captain and named Crew: `@name`, assigned task, repository scope, parent ownership, current lifecycle state, completed work, blocker, next task, and scope alignment. Any assessment of useful work must be grounded in visible task evidence and acceptance proof; never invent a quality score, code volume, completion, or agent performance. JCode’s live Swarm state and Mermaid path remain authoritative.

## Native Swarm integration and agent maximizing

Crew names, directs, and monitors the agents JCode Swarm already creates. It does not create a parallel agent system. Map each Crew identity to a real native Swarm member and use existing JCode capabilities for:

- direct and scoped communication to a named `@name` member or the Captain;
- real task-DAG assignment, parent ownership, lifecycle, persistence, recovery, and capacity admission;
- live monitoring through the native gallery, transcript, status notices, plan state, and Mermaid graph;
- evidence-backed accountability: task scope, accepted result, blocker, handoff, and next responsible owner.

Use **agent maximizing** to mean applying JCode’s verified available capacity to genuinely independent, well-scoped tasks with an accountable parent and an acceptance proof. It does not mean maximizing token consumption, fabricating activity, or expanding the Crew beyond native admission, task, or recovery limits.

Before proposing a Crew implementation, inspect the local JCode master source and documentation for Swarm seams, then use official JCode GitHub material only if the local source lacks the answer. Search the real Swarm command, task-DAG, member, channel, persistence, recovery, gallery, status, and Mermaid paths. Reuse those production seams; do not reverse-engineer a replacement outside JCode.

## Build-slice workflow

1. Read the Captain’s requested outcome and identify the affected Crew surface: native `/crew create` command, Captain or named-Crew setup, JCode Swarm behavior, Crew Watch lifecycle/receipt/wake supervision, Mermaid projection, Crew Map, private Sites presentation, terminal view, or documentation.
2. Read the controlling Crew record and current evidence. Treat `records/crew-constitution.md` as the baseline authority for the thin native build; flag any conflict with a newer explicit Captain direction instead of silently blending them.
3. Define one bounded slice: user-visible behavior, native JCode seam, required proof, durable-state or wake requirement if any, non-goals, risk, stop condition, and the exact owner.
4. If the request requires Crew code, create a concise scoped instruction for JCode. JCode implements and validates Crew code, owns Crew Map, and runs No Mistakes. Codex does not code Crew, run No Mistakes, or publish an official Crew transition.
5. If the request affects the private Crew Overview Sites workspace, use Crew Stats and Sites for the presentation portion only. Keep it sourced and read-only; do not substitute it for native JCode execution.
6. Return a handoff that states: requested outcome, evidence used, scope, explicitly deferred work, JCode action, proof expected, and the next Captain decision.

## Guardrails

- Preserve `/swarm` and JCode’s real DAG, channels, persistence, recovery, cockpit, and Mermaid paths. Do not propose a second scheduler, database, runtime, agent system, or graph renderer.
- Do not turn a future target into a claim of current implementation. Mark it **future**, **proposed**, or **verified**.
- Use First Mate only as a research reference for supervision patterns; do not copy its Bash watcher into Crew or claim parity without a verified JCode seam. Do not introduce Lavish or Instatic. Use ChatGPT Sites for optional Crew product presentation and Visualize only when the Captain requests an interactive in-conversation visual.
- Do not make code changes, commits, tests, reviews, pushes, releases, or No Mistakes actions for Crew. Send the approved, bounded request to JCode instead.
